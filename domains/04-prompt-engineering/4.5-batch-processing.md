# 4.5 Batch processing

## Message Batches API — constraints (memorise)

- About **50% cheaper**
- Completes **within 24 hours**
- **No** latency SLA
- **No** multi-turn tool calling **inside one batch request** (your retry loop is a *new* request, or you stay synchronous)
- **`custom_id`** correlates request ↔ result

## Matching rule (sample Q11)

| Workload | API |
|---|---|
| Developers waiting (PR review, pre-merge) | **Synchronous** |
| Overnight reports, weekly audits, nightly test generation | **Batches** |

A manager who “batches everything for savings” is wrong for **blocking** workflows. Batch the nightly audit; keep PR review sync.

Do not invert (batch PRs, sync the nightly job).

## Submission frequency from an SLA

Batches may take the full **24 hours**, so the worst case for a document is *wait for the next submission* + *24 h processing*.

**Rule:** submission interval ≤ SLA − 24 h.

Promised turnaround 30 h → submit at least every **6 h**. The guide's example uses **4-hour windows** to guarantee a 30-hour SLA — 4 + 24 = 28 h worst case, leaving 2 h slack for resubmitting failures. A 24-hour SLA cannot be met with Batches at all; stay synchronous.

## Failure handling

- Find failures by **`custom_id`**
- Resubmit **only** those (chunk oversized documents, fix prompt) — not the whole 10k
- **Refine on a sample** before the big batch so first-pass success is high

## Practice

Manager: use Batches for (a) every-PR review and (b) nightly codebase audit.

**Correct recommendation:** batch **(b) only**. (a) is blocking.

## Check questions

1. Why is Batches a poor fit for a validation-retry loop that needs three tool-use turns on one document?
2. 200 of 10,000 IDs fail. What do you resubmit?
3. The SLA is 36 hours. What is the longest safe interval between batch submissions, and why?
